# BolidGrid: инструкция для ИИ-сессий

Этот файл — входная точка для будущих ИИ-ассистентов и разработчиков. Сначала прочитайте его, затем затрагиваемые модули и тесты. Не переписывайте архитектуру без отдельного запроса пользователя.

## 1. Назначение и главный сценарий

BolidGrid — браузерный редактор монтажного плана стены. Главная задача: **согласовать расположение приборов вместе с кабельными коробами**, задать понятные размеры и подготовить лист/спецификацию.

Приоритеты при изменениях:

1. корректная геометрия и сохранность проекта;
2. удобное точное позиционирование по горизонтали и вертикали;
3. комфортная работа в браузере телефона;
4. простой интерфейс без лишних режимов;
5. обратная совместимость JSON и предсказуемый экспорт.

Это статическое приложение: **Vanilla JavaScript, ES modules, SVG, CSS**. Нет React, TypeScript, Vite и production-сборки. Не добавляйте фреймворк или обязательный бандлер для локальной функции.

## 2. Запуск и проверка

Требуется Node.js 20+.

```bash
npm install
npm start                         # http://localhost:8080
npx playwright install chromium   # один раз на новой машине
npm test                          # базовый редактор
npm run test:qa                   # расширенные сценарии
npm run test:mobile               # 390×844, 360×780, 412×915
npm run test:all                  # все три набора последовательно
```

Тесты сами поднимают локальный сервер. Их снимки и выгрузки попадают в `tests/output/`; этот каталог не коммитят.

Перед завершением содержательного изменения:

- запустите хотя бы затронутый набор, а перед релизом — `npm run test:all`;
- выполните `git diff --check`;
- откройте реальный UI и посмотрите desktop и phone screenshots;
- убедитесь в отсутствии `pageerror` и `console.error`;
- обновите `docs/USAGE.md`, `docs/DATA-MODEL.md`, `docs/QA-REPORT.md`, если изменились поведение, формат или результаты проверок.

Не сообщайте об успешной публикации, если фактически выполнен только локальный commit или сохранён предпросмотр.

## 4. Система координат и геометрические инварианты

Все проектные размеры — **целые миллиметры**.

- Стена: `width` по X, `height` по Y.
- Прибор: `x` — левая грань от левого края; `y` — **нижняя грань от пола**.
- Экранная SVG Y: `wall.height - y`.
- Габариты не хранятся в устройстве: их даёт `getModel(device.modelId)` из каталога.
- `rot` существует в данных, но текущий монтажный сценарий рассчитан на фронтальное размещение без свободного поворота геометрии.
- Короб: `points: [[x,y], ...]`; каждый соседний сегмент строго горизонтален или вертикален. Ширина `width` участвует в привязках и проверке пересечений.
- Размер: `a`, `b` в той же системе; основной сценарий — горизонтальные и вертикальные линии.
- Приборы и трассы ограничиваются границами активной стены.
- Касание границ не считается пересечением: используется строгое AABB-overlap, а не `<=`.

При точном вводе поддерживаются отсчёты:

- X: левый край / центр / правый край прибора;
- Y: низ / центр / верх прибора.

Пересчёт обязан учитывать реальный габарит, округлять до миллиметров и ограничивать результат стеной. Групповой зазор измеряется **между габаритами**, не между центрами. Если вся группа не помещается, операция отклоняется целиком.

## 5. Состояние, история и сохранение

`Store` — источник истины. Не создавайте параллельное долгоживущее состояние в DOM или редакторе.

- Изменения проекта выполняйте через методы Store и `act(...)`, чтобы получить один понятный шаг undo/redo.
- Один пользовательский смысловой шаг должен быть одним снимком истории. Например, две автоматические размерные линии отменяются вместе.
- Проект автосохраняется в `localStorage`; это не облачная синхронизация.
- Экспорт/импорт JSON использует `schema: 1`. Не меняйте существующие значения полей молча.
- При расширении схемы добавьте нормализацию старых данных, тест импорта и обновите `docs/DATA-MODEL.md`.
- Импорт — недоверенный ввод: санитизируйте числа, строки, ID, координаты, типы и границы. Пользовательский текст выводите через экранирование/безопасные DOM API.
- Производные данные не сохраняйте: временные отступы, smart guides, выделение, viewport, черновик трассы и список пересечений вычисляются заново.

`findPlacementIssues()` возвращает текущие пересечения приборов друг с другом и с полосой короба. Это вычисляемая проверка, а не часть JSON.

## 6. UI и мобильные правила

Не ломайте существующие состояния интерфейса:

- desktop: каталог слева, лист в центре, свойства/спецификация/короба справа;
- phone: одна колонка, нижняя навигация и прокручиваемые нижние шторки;
- `#selection-dock` показывается только при выборе в инструменте `select` и не должен закрывать «Готово», статус или навигацию;
- обычная подсказка скрывается при выборе, но подсказка с рабочей `.hint-btn` остаётся;
- `.toast` имеет `pointer-events:none` — уведомление не должно перехватывать касания;
- используйте `100dvh` и `env(safe-area-inset-bottom)`;
- основные сенсорные цели — около 44 px;
- у контейнеров сетки сохраняйте `min-width:0`/`minmax(0,1fr)`, чтобы не появлялось горизонтальное переполнение;
- `[hidden]` должен реально скрывать элемент независимо от других `display`-правил.

Модальные окна поддерживают Escape, backdrop, крестик, начальный фокус и возврат фокуса. Сохраняйте это поведение для новых диалогов.

После изменения CSS или жестов проверьте не только открытие панели, но и реальные tap/drag/pinch на всех трёх mobile viewport’ах. Элемент может существовать и быть видимым, но перехватываться другим слоем — при сомнениях проверяйте `document.elementFromPoint()`.

## 7. SVG и экспорт

Рабочий SVG содержит служебные узлы, которых не должно быть в выгрузке:

- selection/resize/hit helpers;
- smart guides;
- временные отступы;
- `.issue-frame` и другие рамки проверки;
- интерактивные маркеры и черновики.

При добавлении служебного класса обновите очистку `buildExportSVG()` и smoke-тест. Экспортируемый SVG должен оставаться самостоятельным и валидным XML. CSV использует разделитель `;` и BOM для Excel. Имена файлов нормализуются в ASCII, чтобы браузер не терял расширение у кириллического имени.

## 8. Как безопасно вносить изменения

1. Сформулируйте пользовательский сценарий и инвариант, который нельзя нарушить.
2. Найдите существующий метод Store/редактора; не дублируйте геометрию в панели.
3. Добавьте минимальное изменение и тест на успех, границу и отмену.
4. Для новой операции проверьте: состояние, undo/redo, перезагрузку, SVG/JSON и телефон.
5. Не удаляйте существующие проверки только ради зелёного прогона. Обновляйте тест лишь при осознанном изменении контракта.
6. Для визуальной правки выполните цикл «рендер → снимок → причина дефекта → исправление → повторный снимок».
7. Не оставляйте диагностические `console.log`, временные файлы и generated output в Git.

## 9. GitHub и секреты

- Основная ветка публичного репозитория: `main`.
- Pages публикует статические файлы через `.github/workflows/pages.yml`.
- Workflow `tests.yml` запускает браузерные проверки для push и pull request.
- README должен показывать актуальный интерфейс; снимки лежат в `docs/assets/`.
- Не записывайте GitHub tokens, пароли, cookies и другие секреты в код, README, документацию, тесты, screenshots, Git history или ответы пользователю.
- Не выдумывайте успешный push, metadata update или deploy. Сообщайте только подтверждённый результат.

## 10. Что не следует обещать

BolidGrid не выполняет нормативный расчёт, не проверяет проект по СП и не гарантирует актуальность каталожных габаритов. Проверка пересечений — геометрическая помощь при согласовании. Автосохранение локально; физические iOS/Android-устройства и реальный принтер не заменяются Chromium-тестами.
